# CLAUDE.md

## Rules

### Bash
- Never use sed, find, awk, or complex bash commands
- Never chain commands with &&
- Never chain commands with ;
- Never pipe commands with |
- Never read or write from /tmp. All data lives in the project.

### Memory rules
Do not use your Memory functionality. Update CLAUDE.md instead. This project is developed across several hosts and several users. Memories do not transfer across hosts or users. CLAUDE.md does.

### Bash rules
- Never capture stdout into env vars (`UUID=$(...)`).
- Never run raw cargo, curl, pkill. Use `brokkr`. **This means never, including
  during iteration.** `cargo build` / `cargo test` while working, "just to check
  quickly", is the same violation as shipping with them - `brokkr` is the only
  supported entry point, and reaching past it means running a different build
  configuration from the one that gates the commit. The mapping is total; there
  is no case that needs raw cargo:

  | instead of | run |
  |---|---|
  | `cargo build` / `cargo clippy` / `cargo test` | `brokkr check` (gremlins + clippy + tests, the full gate) |
  | `cargo test <name>` | `brokkr test <name>` |
  | `cargo test <name>` repeatedly (flaky hunt) | `brokkr test <name> -N <count>` |
  | `cargo run -- <args>` | `brokkr run -- <args>` |
  | `cargo fmt` | `brokkr fmt` |
  | `cargo install --path .` | `brokkr install` |

- `brokkr check` is the gate; run it before every commit, not just at the end.
- `brokkr test <NAME>` is a substring filter over the package's unit *and*
  integration tests, release profile by default (`--debug` for dev). It always
  passes `--include-ignored --nocapture --test-threads=1`.
- **There is a 20-second per-test watchdog**, shared by `brokkr check`'s test
  phase and `brokkr test`. A test that runs longer is killed and reported as
  hung. `brokkr test --timeout <SECS>` raises it to at most 280s, and only for a
  name that matches exactly one test. This is why fixture timings in
  `src/provider_tests.rs` are injectable rather than real-world durations - a
  test that waited out the production 10s `SIGKILL` escalation would sit right
  under the ceiling and eventually trip it on a loaded machine.
- `brokkr man` lists bundled docs (`man check`, `man config`, `man clippy`,
  `man run`, `man results`, ...). Read those rather than guessing at flags.
- Waiting on a long command: just run it and stop. It wakes you on exit. Never
  poll it with `sleep`, `until`, or a watch loop.

### git commit rules
- Always run `brokkr fmt` before a commit.
- Never commit markdown changes and/or results.db alone. Bundle them with upcoming code commits.
- When committing other changes: always tag along brokkrs 'results.db' and markdown files if dirty.
- Write substantive engineering-focused commit messages.
- Has `Cargo.lock` changed? Commit it.
- Never `git push` unless the user explicitly asks. Stop after the commit.

### Subagents- Do NOT use worktree isolation for parallel agents. Worktrees create merge conflicts that silently drop agent work. Instead, launch agents in the same tree with strict file ownership - zero overlap.

## What this project is

A Rust CLI (`review`) that fans out code reviews to fresh AI sessions across providers (Claude Code, Codex). It's a prompt builder - the agents fetch code themselves. Each run starts a clean session primed with an archetype's prompt (see Design decisions for why fresh beats long-lived).

Per-project config via `.review.toml`: archetypes (name → priming prompt), groups, default providers, and host-scoped `--profile` overrides. Comma-separated archetypes/groups can be mixed freely, with deduplication.

## Build and run

`brokkr` is the only entry point - never raw `cargo` (see Bash rules for the
full mapping and the 20s per-test watchdog).

```
brokkr check                    # the gate: gremlins + clippy + tests
brokkr test <name>              # one test by substring; -N <n> to repeat
brokkr run -- <args>            # run the binary
brokkr fmt                      # before every commit
brokkr man check                # bundled docs for the pipeline
```

```
brokkr check
review init
echo "review for issues" | review security
```

Single binary crate, no workspace.

## Architecture

- `src/cli.rs` - Clap CLI. Archetype is a positional arg; `init` and `sessions` are subcommands.
- `src/config.rs` - Parses `.review.toml` in cwd. `[archetypes]` maps name → priming prompt; `[_groups]` names archetype sets; `[_defaults].providers` is the provider list when `--provider` is omitted; every other top-level table is a hostname carrying `[<host>.<provider>.<profile>]` profiles (model/effort/sandbox/env/`config`, the last being verbatim codex `-c` overrides). Parsed by peeling reserved sections off a `toml::Table` and treating the rest as hosts (serde `flatten` can't coexist with the sibling `archetypes` field). Also holds `generate_uuid`/`generate_short_id`. Uses `toml` and `gethostname` crates.
- `src/input.rs` - Reads stdin instructions (required, 20KB limit).
- `src/prompt.rs` - `assemble`: archetype prompt + `\n\n` + stdin. No baked-in grounding; the archetype prompt owns role and read/write intent. Special case: a **bare single-line slash-command** prime (e.g. `goal = "/goal "`) inlines the stdin onto the command's line (`/goal <stdin>`) instead of the blank-line separator, because the claude/codex harness only treats same-line text as the slash command's argument - a blank-line gap fires the command argument-less and orphans the operator's goal below.
- `src/provider.rs` - Async provider invocation for claude, codex and grok. Prompts piped via stdin, except grok (which takes no stdin prompt - see its bullet below - and gets a `--prompt-file`). Each run (oneshot=true) starts a fresh persistable session (claude `--session-id <generated UUID> --permission-mode dontAsk`, codex `exec --json` to capture `thread_id`, grok `--session-id <generated UUID> --output-format json --permission-mode dontAsk`); `--session` resume passes oneshot=false. Profile settings applied: `model` (claude `--model`, codex/grok `-m`), `effort` (claude `--effort`, codex `-c model_reasoning_effort=`, grok `--reasoning-effort`), `sandbox` (codex and grok `--sandbox`, default `read-only`; claude ignores it - its `--permission-mode` is a different axis with no honest mapping), `env`. All three emit the new session ID via `ProviderResult.session_id`. Both codex paths (fresh + `--session` resume) share `run_codex_json`, which streams `--json` and takes `-o`, then distills a `Digest` (exit/signal, `captured` from the `-o`/`--output-last-message` backstop, `recovered_from_transcript`, turn count, summed token usage, non-JSON log lines, `turn_error`, optional transcript forensics) from the NDJSON (`thread.started`/`item.completed` agent_message/`turn.completed`/`error`/`turn.failed`); it does not bail on a non-zero exit so a halted/errored run still reports what it produced. The final-message pick is a three-tier fallback: the `-o` backstop, else the transcript's recovered `final_answer`, else the last streamed message (see Design decisions for why). `run_codex` just builds the args (fresh vs `resume <id>`); the `-o` temp file is created via `new_output_file` with a random UUID name and `O_EXCL`, so concurrent runs can't collide and the predictable path can't be symlink-clobbered. A run that produces no message still returns the digest (with transcript forensics) rather than a bare error. `print_result` renders the digest above the message. The codex child runs with `RUST_BACKTRACE=1` (so a panic is legible) and its stdin-write result is kept (a broken pipe = codex exited first). `DigestSummary` is the flat, serializable projection of a `Digest` (`exit_code`/`signal`/`captured`/`recovered_from_transcript`/`turns`/`task_complete`/`stream_error`/`turn_error`/usage/`incident_path`) persisted into the audit + sidecar logs so failures are greppable after the fact.
- `src/transcript.rs` - Codex on-disk transcript forensics. Locates `$CODEX_HOME/sessions/**/rollout-*-<session_id>.jsonl` by filename (the session ID is captured, so no cwd/mtime heuristic) and parses it for `task_complete`, `stream_error`, the last event, the last in-flight tool call (a `function_call` with no matching `_call_output` = what was running when it stopped), and `final_answer` (the last `agent_message` whose `phase == "final_answer"` - codex tags interim notes `commentary` and the real report `final_answer`). Per-turn state (including `final_answer`) resets on each `task_started` so a resumed rollout reflects the current turn. Scoping a summary to one run's events is the caller's job, via `slice_from_offset(bytes, from_offset)` - the rollout's size at that run's launch, shared with `watchdog` so the two can never disagree about where a run begins. Passing `None` summarizes the whole file (`review sessions <id>`). Read when a run looks wrong (not captured / non-zero exit / signal), so clean runs stay uncluttered.
- `src/incident.rs` - Forensic bundle writer for suspicious codex runs (same `!captured || exit!=0 || signal` gate as the transcript). `write_bundle` dumps `~/.local/share/review/incidents/<utc>-codex-<sid>/` with `stderr.txt` (the channel we used to discard - and with `RUST_BACKTRACE=1` set on the child, a panic lands here with its trace), `stdout.jsonl` (raw NDJSON, last 1 MiB), `transcript.tail.jsonl` (last 80 rollout lines), `prompt.txt` (the exact stdin), and `meta.json` (full argv incl. argv[0], a copy-pasteable `command` string = injected env prefix + quoted argv + `< prompt.txt`, cwd, exit/signal, stdin-write error, durations, `codex --version`, `final_answer_present`/`rate_limits` scanned from the rollout, and profile env - names always, values redacted when the name looks secret). The `command` + `prompt.txt` make the run replayable verbatim (secret env values show as `<redacted>`). `review incidents [--limit N]` lists recent bundles newest-first with a one-line verdict and the bundle path; a recorded `turn_error` *is* the verdict (`turn failed: <msg>`, truncated to one line) and outranks the inferred ones (`no final answer (died)` / `recovered` / `completed (truncated)`), because a bundle codex already explained must not send the reader hunting for a cause; `list_recent` reads each `meta.json` back via `IncidentSummary`. Best-effort: every failure warns, never derails the run. The bundle dir is surfaced on the digest (`incident:` line) and persisted in the sidecar/audit digest.
- `src/watchdog.rs` - Rollout watchdog for codex runs: a single poller over the rollout file that decides whether a silent codex is finished-but-stuck or wedged. "This run's turn" is delimited by a **byte offset** (the rollout's size at spawn), not a timestamp: rollout events carry millisecond stamps while our own clock string is second-resolution, so a prior turn completing in the same second as launch would slip past a time filter and its stale answer would license killing a resume that had produced nothing. The offset is exact and has no such race. The baseline is an `Option<u64>`, and `None` (a resume whose rollout could not be statted before launch) **disables the watchdog entirely** rather than degrading to `Some(0)`: scanning the whole session history would let a previous turn's `final_answer` authorise killing a genuine mid-turn wedge. A fresh run's `Some(0)` is exact, not a fallback - its rollout does not exist yet. One poller, two verdicts (`watchdog::Kind`): **`Stranded`** (answer on disk + quiet ≥ `quiet_grace`) kills and recovers; **`Stalled`** (no answer + quiet ≥ `stall_grace`, default 15 min) kills, bundles, and fails. `Stranded` is explicitly **not** a timeout - it cannot fire on a run that has not already produced its answer, however long that run takes. `has_final_answer` is deliberately separate from `transcript::parse` - parse answers "state of the current turn" (resetting at each `task_started`), the watchdog asks "has this run produced an answer at any point since it began", which must survive the trailing micro-turns codex appends after the substantive turn. Every verdict carries `quiet_secs` and `last_event`, both persisted to the digest and the incident bundle.
- `src/writable_roots.rs` - Derives the writable roots a build needs that live outside the workspace: `$XDG_RUNTIME_DIR` (the build lock - fatal when denied), `$CARGO_TARGET_DIR`, and the resolved `./target` symlink. Keeps only absolute paths already outside cwd (one inside is writable anyway, and granting it would imply a widening that did not happen), normalises trailing slashes so a symlink target and the env var naming the same directory are one grant, and refuses `/`. Profile-supplied roots go through `derive_with`, which expands `~`/`$VAR`/`${VAR}` and refuses an entry whose variable is unset (collapsing it would silently grant `/data` or `/`). `Host` is a trait so the derivation and the expansion are pure functions under test - the developer's own `CARGO_TARGET_DIR` and `HOME` must not decide whether the suite passes. `config_override` renders the codex `-c sandbox_workspace_write.writable_roots=[...]`, TOML-escaping each path; the escaping is tested by *parsing* the result, because a substring assertion cannot distinguish an injected key from the same text safely quarantined inside a string. Applies to `workspace-write` only. See Design decisions for why this ambient coupling is allowed here and nowhere else.
- `src/provider_tests.rs` - End-to-end tests of the codex runner against a **stub `codex`** shell script (included into `provider.rs` as a `#[cfg(test)]` module so it can reach private items). The behaviours under test are *process* behaviours - finishing work then refusing to exit, wedging mid-turn, leaving a descendant that holds stdout open or ignores `SIGTERM` - none of which can be faked with a mocked return value; they need a real child, pipe, process group and kill. `CodexRuntime` (binary, watchdog `Timings`, `drain_grace`, `sigkill_escalation`, `data_root`) is the injection point that makes a 3-minute detection and 10-second escalation resolve in under a second. `data_root` is load-bearing, not tidiness: `CODEX_HOME` only redirects the *child*, so `review`'s own paths otherwise resolve from the real `HOME`/`XDG_DATA_HOME` - an earlier version of this suite wrote stub incident bundles into the operator's real `~/.local/share/review/incidents`. Coverage: stranded completion is killed and recovered; a mid-turn wedge trips the stall timeout (killed, bundled, *no* answer recovered, `quiet_secs`/`last_rollout_event` recorded); a disabled stall timeout never fires; an advancing rollout is never killed (answer present *and* still writing - the advancement gate, not the answer gate); a pipe-retaining child blocks neither reaping nor output capture; group escalation actually reaps a `SIGTERM`-ignoring descendant; a refused turn (`error` + `turn.failed`, exit 1, no `final_answer` on disk) carries its stated reason into the digest, the summary and `meta.json` while keeping the rest of its failure signature. Scratch lives in `target/test-scratch/<uuid>/`; stubs record any deliberately-left-running pid to `$LINGER_PID` so tests clean up after themselves.
- `src/inflight.rs` - Marker files at `~/.local/share/review/inflight/<session_id>.json` written once a run's session ID is known and removed when it returns, so `review sessions` can print `[in flight] ... turn in flight since <age>`. The sidecar is only written on return, so without this a running (or wedged) turn is indistinguishable from an idle session showing its previous response. Each marker records the owning `review` pid; `read_live` treats a marker whose pid is gone as stale, and deletes it. The session ID is validated as a bare filename component (alphanumerics, `-`, `_`) before being used as a path - it arrives straight from `--session <id>`, whose validation `review` otherwise delegates to the provider, so unchecked it let `--session ../foo` escape the marker directory and write then *delete* a file elsewhere. An allowlist, not a `..` denylist, because only the former is safe by construction. Best-effort throughout - never derails a run.
- `src/sessions.rs` - Append-only sidecar log at `~/.local/share/review/sessions.jsonl` (or `sessions-private.jsonl` if `audit.private`). One row per run that captured a session ID (`kind = "run"`), one per `--session` resume (`kind = "session"`). Rows carry timestamp + epoch_secs, project, hostname, audit_id, provider, archetype, session_id, model, env var *names* (not values - those can carry secrets), the `sandbox` level the run launched with and any derived `writable_roots`, operator prompt, assembled prompt, response or error, review version, and (codex) the flat `DigestSummary`. Read helpers (`read_all`, `latest_for_session`, `age_secs`, `format_age`) drive the cache-age gate in `--session` mode and the `review sessions` subcommand.
- `src/config_write.rs` - `append_audit_id` (the only writer left; archetypes/profiles are hand-edited).
- `src/main.rs` - Wires CLI to config, prompt assembly, and provider dispatch. Also prints the trailing `runtime:` line: a wall clock started before `Cli::parse()` and printed after the last result on both the fan-out and `--session` resume paths (`format_runtime`). It deliberately spans stdin read + global-lock wait, so it's what the operator waited, not provider time; the subcommands (`init`/`sessions`/`incidents`) return before it.

## Design decisions

- Every run starts a fresh session - archetype priming prompt + stdin. Reviving a long-lived session on a cold cache reprocesses its ever-growing history; a fresh session costs ~one review's worth of tokens and can't act on stale accumulated context. The session is persistable and its ID is printed so follow-ups can go through `--session` while the cache is warm.
- No baked-in grounding prefix. It was written for long-lived read-only review sessions (anti-staleness + "don't modify files"); fresh-per-run made the anti-staleness lines dead and workspace-write made "don't modify files" wrong. Archetypes now own their own grounding.
- Archetypes are pure: `[archetypes]` name → prompt, no host/session binding. Overrides live in separate host-scoped named profiles (`[<host>.<provider>.<profile>]` carrying model/effort/sandbox/env) selected with `--profile <name>`; `--profile` requires the table to exist for every launched provider or the run errors. `sandbox` defaults to `read-only`, so a bare run can never modify files; a profile opts up to `workspace-write`. Claude ignores it - its `--permission-mode` is a different axis (tool-approval, not a filesystem sandbox) with no honest mapping.
- **`sandbox` is `review`'s own vocabulary, translated per provider by `config::sandbox_for`.** The levels (`read-only`, `workspace-write`, `danger-full-access`) are codex's names, kept because they were the documented config surface before translation existed - a fresh set would have silently changed the meaning of every profile already written. Codex takes them verbatim; grok's built-ins are `read-only`/`workspace`/`none`, so the upper two are rewritten. This is not cosmetic: grok cannot resolve an unknown profile name and **refuses to start**, so before the mapping a profile written for codex broke the moment it was pointed at grok, at launch, with an error that reads as a missing config file. `read-only` happens to be spelled identically everywhere, which is why the *default* path was portable by luck rather than design - only an explicit write opt-up ever hit the mismatch. An unrecognised value is passed through verbatim rather than rejected, because grok resolves names against user-defined profiles in `~/.grok/sandbox.toml`: rejecting it would make `review` the reason a valid provider config could not be used, and the provider validates its own vocabulary with a better error than we could write (and fails before running a turn, so a typo is cheap). The three level names are therefore **reserved** - a custom grok profile named `workspace-write` or `danger-full-access` cannot be selected from a `.review.toml` profile. That is the deliberate trade: the point of the levels is that they mean the same thing whichever provider a profile is pointed at, which fails the moment one provider can reinterpret them. Custom profiles have the rest of the namespace.
- Providers resolve from `--provider`, else `[_defaults].providers`; empty → error.
- `--session <id>` resumes a specific provider session and sends raw stdin - bypasses `.review.toml`, no prime, no profile. `--provider` is a *filter over a known answer* rather than a declaration: a session belongs to exactly one provider and the sidecar records which, so `resolve_session_provider` infers it when `--provider` is omitted, and accepts a list that contains the owner (`--provider claude,codex` against a codex session is not ambiguous - only codex can resume it, and those flags carry over verbatim from the fresh run that created the session). What stays an error is a genuine contradiction (a `--provider` the session does not belong to) or genuine ambiguity (several names, no sidecar record to choose between them). A recorded provider is still validated against `KNOWN_PROVIDERS`, so a row naming a removed provider (kilo/opencode) can't be inferred into an unrunnable invocation. Validation of the session ID is delegated to the provider. Before invoking, `review` looks up the sidecar log for the last-touched time: `--session` is the *warm* path, so if the session last ended > 55 min ago (`timings::STALE_SESSION`, past the realistic prompt-cache TTL) it **errors out** and tells the operator to do a fresh run instead of paying to reprocess a cold prefix. No sidecar record -> age unknown -> proceed. What refreshes the last-touched clock is *any resume that ran* (`resume_ran = output.is_ok()`), not just one that produced a good answer: the clock tracks prompt-cache warmth, and reprocessing the prefix warms the cache even on a codex mid-turn death (which returns `Ok`-with-a-death-digest). Gating refresh on answer quality would pin the clock to the last *successful* touch and wrongly refuse the next resume of a genuinely-warm session as stale; only a hard launch failure (`Err`, cache never warmed) skips the refresh.
- Codex `exec --json` runs fail two distinct ways, both surfacing as `exit 1 / captured false / turns 0` on stdout. (1) *Truncated-but-completed*: the model produced a real `final_answer` on disk but codex exited non-zero at shutdown, dropping the closing stdout events and the `-o` file. (2) *Genuine mid-turn death*: no `final_answer` was ever produced - the turn was cut off after a tool call. **`task_complete` does not tell these apart** - it fires on aborted turns too; the authoritative signal is `task_complete.last_agent_message` (== the rollout's `final_answer` `agent_message`), which is `null` on a death. So `review` keys recovery on `final_answer`, not `task_complete`: recovery is scoped to the bytes *this run* appended (the same `rollout_baseline` byte offset the watchdog uses, not a wall-clock stamp - a second-resolution stamp let a prior answer written in the same second as a resume's launch be recovered as the new run's result, suppressing auto-resume and writing a wrong response into the sidecar; an untrustworthy baseline scopes to `u64::MAX`, i.e. recovers nothing, because no recovery beats a wrong answer). When it exists (including from a later `--session` resume of the same session) it's restored from the rollout instead of surfacing the last streamed `commentary` (an interim "I am now doing X" note); when it's absent the run genuinely died, `review` keeps the interim text but the digest note says "died without a final answer" (exit status distinguishes a death from a benign no-answer). Why codex exits 1 / dies is codex-side and is *not* recorded in the rollout - no `stream_error`, abort, or rate/context-limit event; recovery salvages output but does not explain the death.
- Auto-resume is the "work around" for a codex mid-turn death: a fresh codex run that ends with no real final answer (`!captured && !recovered_from_transcript`, `died_without_answer`) is resumed **once**, immediately (cache still warm), inside the same spawned task so the profile model/effort/sandbox/env are reused, with a fixed nudge (`RESUME_NUDGE`). If the resume produces a real answer (`got_final_answer`) it replaces the dead result, prefixed `(auto-resumed after the initial run died...)`; otherwise the original dead result stands. **A run carrying a `turn_error` is excluded** (`stated_failure`): see the refusal decision below. A manual resume is exactly what rescued the original Death 2. It calls `provider::invoke` directly, bypassing the `--session` cold-cache gate (that gate guards a *cold* manual resume; this one is warm by construction). Always on.
- **A stated failure is not a death, and is never retried.** Codex ends a turn it will not do with a stream `error` + `turn.failed` pair carrying the same message (an upstream refusal - content flagged, rate limit, auth - or a harness error). `review` dropped both event types, so a fully-explained refusal surfaced identically to an unexplained mid-turn death: `exit 1 / captured false / turns 0`, the note "died without a final answer", the last interim commentary presented as the result, an incident bundle filed under the hang class, and - because `died_without_answer` was true - an auto-resume straight into the identical refusal. That last part is the signature: **every field occurrence left two bundles seconds apart**, which reads as two deaths and is really one refusal retried. The message is now carried on `Digest.turn_error`, printed first (`turn failed: <msg>`) since the operator's next move follows from the message rather than the exit status, persisted flat (`jq 'select(.digest.turn_error != null)'`), recorded in `meta.json` where it becomes the `review incidents` verdict, and used to gate auto-resume (`stated_failure`). The retry gate is the substantive half: auto-resume exists for the mid-turn wedge, where the work was real and interrupted so replaying it can finish the job; a stated failure is a verdict on the request itself, so resending it costs a second full run to be told the same thing. What deliberately does *not* change: the run still exits 1 (a refusal produced no work and must not report success to CI), and it still writes a bundle (the evidence is worth keeping) - the bundle just no longer masquerades as a hang. Observed on codex-cli 0.146.0 and unrelated to the 0.147.0 hang class; the process exited promptly and cleanly on its own.
- A suspicious codex run writes a full forensic bundle (`src/incident.rs`), because the death investigation kept stalling on information `review` discarded: codex's stderr, the raw NDJSON stream, whether the prompt finished writing, and (absent `RUST_BACKTRACE`) any panic trace. The bundle over-instruments the *next* death so it's diagnosable without a repro. It's the "catch" half of the strategy; recovery (final_answer) is the "work around" half. Root-causing codex itself is explicitly out of scope.
- **codex 0.147.0 can finish a turn and never exit.** Two hangs were diagnosed on 0.147.0 against sessions that worked on 0.146.0. (1) *Stranded completion*: every turn reached `task_complete` with a non-null `last_agent_message`, the rollout then stopped advancing, and the process hung 10+ hours with the answer on disk the whole time. (2) *Mid-turn wedge*: the rollout stopped mid-turn with 25 unified-exec background cells running. Leading upstream explanation for (1) is the resume-only `exclude_turns: true` that `codex exec`'s `thread_resume_params_from_config` began sending in 0.147.0 (openai/codex#35621): after `TurnCompleted`, exec issues an unbounded `thread/read` with `include_turns: true` (`maybe_backfill_turn_completed_items`) while its single `select!` loop is not draining notifications, and with turns excluded at resume that read must rebuild the whole thread history from the rollout - which fits "resumes hang, fresh runs don't, small sessions are fine". Secondary candidate: `OtelProvider`'s `Drop` shutdown, bounded for the TUI only by openai/codex#37109 - `codex exec` still drops it synchronously, and a Statsig metrics exporter is on by default in release builds. Neither is proven; root-causing codex is out of scope. `review` catches it rather than explains it.
  - The old `join!` on child-exit **plus both pipes** made this unsurvivable: everything `review` knows about a run (digest, transcript, incident bundle, sidecar row) is computed after that join, so a wedged run produced no output, no error and no incident bundle. The wait is now a `select!` loop that breaks on reap, with the watchdog able to pre-empt it. Pipe EOF is no longer required to finish - reaping is authoritative, and the readers get a 5s drain grace (defence in depth: 0.147.0 has no production `Stdio::inherit` on the exec path, so a descendant holding the pipes is not a known live path). Readers append into a shared buffer instead of returning at EOF, so a grace-period expiry keeps whatever was captured rather than discarding the stream; the reader is `abort()`ed rather than detached by dropping its `JoinHandle`. The session ID is published on a watch channel the instant `thread.started` is seen, so it survives a truncated capture - losing it would cost the transcript, the recovery path and the sidecar row.
  - `Digest.terminated_by_review` records that *we* killed the run and why, because otherwise a watchdog kill is indistinguishable from codex dying on its own - the exit/signal describe our kill, not codex's fate. Persisted flat, so `jq 'select(.digest.terminated_by_review != null)'` finds the hang class.
- **The stall branch is a timeout, and is named one.** `Stalled` rests on an *empirical* property of codex rather than a documented contract: codex cannot stay silent - it wakes itself every 2-5 minutes even while babysitting a long-running task (the field rollout shows `wait` calls with `yield_time_ms: 30000` and events landing every 5-15s throughout the working portion), whereas the wedge was silent for hours. Two to three orders of magnitude separate them, which is what makes a 15-minute default safe and what made a `/proc` CPU-liveness check unnecessary (it would have added platform-specific complexity for a weaker signal: healthy API waits are CPU-idle and broken processes can spin). The asymmetry is codex-specific: claude legitimately goes silent waiting on a backgrounded task, and none of this runs for claude anyway - it has no rollout. Because the invariant is empirical, it is named `stall timeout` rather than something softer (a future cadence change must be diagnosable, not mysterious), it is tunable and disableable via `[_defaults].stall_timeout_secs` (`0` = off), and `quiet_secs` + `last_rollout_event` are recorded on every verdict so a misfire shows how close the call was and what codex was last doing.
- A stalled or dead run returns `Ok` (so its session ID, digest and incident survive) but exits **1**, on both the fan-out and `--session` paths. Exiting 0 on a wedged run lies to scripts and CI.
- Codex is spawned with `process_group(0)` so it and everything it spawns (exec-server, unified-exec cells, MCP servers) can be signalled as a unit - a wedged codex usually still has live children, and killing the pid alone orphans them. The cost is that a terminal SIGINT no longer reaches codex implicitly, so `provider::install_signal_supervisor` installs **one** process-wide SIGINT/SIGTERM handler that kills every live codex group and then exits 130/143. It must be global, not a per-run `select!` arm: tokio's signal registration is process-wide and permanent, so a per-run handler would leave `review` silently ignoring every SIGTERM after its first codex invocation - *harder* to kill than before. The final SIGKILL sweep uses the *original* snapshot of live groups, deliberately not a fresh read: if codex exits promptly on SIGTERM its waiter unregisters the group, so a re-read would omit exactly the case that matters - a descendant that ignored SIGTERM and is still alive - and `process::exit` cancels `terminate_group`'s deferred escalation. Exiting forfeits the interrupted run's digest/bundle, which is the right trade: the operator asked to stop, and the rollout is on disk for `review sessions <id>`.
- `--session` releases the global lock **once the provider process has spawned**, not when the run finishes, matching the fan-out path (which releases once its staggered launches have fired). The lock spaces out launches, and a resume launches one thing, so there is nothing left to serialize once it runs; holding it for the turn meant one wedged resume froze all `review` traffic on the host indefinitely. A hung run should cost you that run, not the tool. Release is driven by a launch handshake (`provider::LaunchSignal`, a oneshot sent right after `cmd.spawn()`) rather than by dropping the lock before calling `invoke` - the latter leaves a critical section guarding nothing, letting every queued resume through to spawn simultaneously. A dropped sender (failed spawn) releases it too.
- A turn that aborts without carrying a user request or model output is codex's shutdown-time phantom, not a real turn: 0.147.0 opens a turn during `codex exec` teardown and aborts it within milliseconds. It is **not** an empty event sequence - the observed shape is `task_started`, `turn_context`, a synthetic `role: "developer"` message whose text is `<turn_aborted>`, then `turn_aborted` - so "zero items" cannot be the test. What distinguishes it is the absence of both a `user_message` (every real turn is opened by one) and any model output, so `transcript::parse` keys the rollback on a positive list of real-content events (`user_message`, `agent_message`, `reasoning`, tool calls/outputs, `task_complete`, `stream_error`, and `message` with a non-`developer` role). Attributing the phantom made fully-completed sessions report `task_complete=false` - which sent the hang investigation chasing a non-existent "truncated turn" condition. A turn cancelled early but carrying real content is a genuine interruption and is kept.
- The digest is persisted (flat `DigestSummary`) into the audit + sidecar logs. Before this, `run_codex_json` returned `Ok` on any mid-run death and the digest was print-only, so a dead run was filed as a clean short `response` with `error: null` - invisible to `jq`. Now `jq 'select(.digest.captured==false)'` (or `.digest.stream_error==true`) finds them. The run still returns `Ok` (never `Err`) so the session ID + digest survive; the digest fields, not the `error` field, carry the failure.
- `review sessions` lists recent sessions for the current project (or `--all`), grouped by session ID, sorted by most recent touch. `review sessions <id>` shows one session's artifacts on demand: its persisted digest, the on-disk codex rollout transcript (path + task_complete/stream_error/last_event/last_in_flight_tool), and the final response - preferring the transcript's `final_answer` over the sidecar `response`, so even rows recorded before runtime recovery landed surface the real answer. Output is block-formatted for terminal reading; ad-hoc queries beyond that go through `jq` on the JSONL directly.
- **Codex is always passed `--skip-git-repo-check`.** `review` is routinely launched from an umbrella directory that is not itself a git repo but whose repos live in subdirectories (`~/Programs/PRs`, holding `PRs/projects/<repo>`); codex refuses to start there with *"Not inside a trusted directory and --skip-git-repo-check was not specified."* Marking the directory `trust_level = "trusted"` in `~/.codex/config.toml` does **not** help - verified on codex-cli 0.149.0 against two separately-trusted non-repo directories, both refused - so the git-repo precondition is checked ahead of, not satisfied by, project trust, and there is no config-side fix. Waiving it costs nothing we rely on: the filesystem guarantee is `--sandbox` (default `read-only`), a different mechanism that this flag does not touch. All it waives is codex's own "am I in a repo?" question, whose answer was never load-bearing for a tool that only builds prompts.
- **Codex is always passed `-c approval_policy="never"`, because `--sandbox` alone stopped being a filesystem guarantee in codex 0.150.x.** What made `--sandbox read-only` absolute was never the sandbox on its own: it was the headless approval policy. `codex exec` sets `approval_policy = "never"` in its `ConfigOverrides`, and under `never` the model's `request_permissions` escalation is short-circuited to an empty grant (`session::request_permissions_for_environment`), so a read-only run has no path to widen its own permissions. 0.150.x added `build_exec_config`, which **discards that headless default and rebuilds the config with `approval_policy: None`** whenever the resolved `approvals_reviewer` is `auto_review` - a setting an operator can turn on globally in `~/.codex/config.toml`, with nothing on the `review` command line hinting at it. The policy then falls back to `on-request`, escalations route to codex's own auto-approving guardian rather than to a human, the guardian grants them, and the granted `AdditionalPermissionProfile` is layered onto the read-only profile for the turn. Verified on codex-cli 0.150.1: a bare `codex exec --sandbox read-only --skip-git-repo-check` asked to create a file created it; the same invocation plus `-c approval_policy="never"` was rejected with *"patch rejected: writing is blocked by read-only sandbox; rejected by user approval settings"*. The `-c` override survives because `build_exec_config` only rewrites the harness overrides, never the CLI ones. This is why `review` pins the policy rather than trusting the provider's headless default: the guarantee `.review.toml` profiles advertise must not depend on an unrelated key in the operator's global codex config. It is passed **before** profile `config` overrides, so a profile that genuinely wants approvals can still opt back in with a later `-c`.
- **Codex is always passed `--ignore-rules`, because an operator's execpolicy allowlist silently disables the sandbox outright.** This is the second, independent hole in the same guarantee, and unlike the `auto_review` one it had been firing in the field for months. Codex's `$CODEX_HOME/rules/*.rules` are not merely an approval allowlist: when a `prefix_rule(..., decision="allow")` matches **every** parsed segment of a command, `exec_policy.rs` returns `Skip { bypass_sandbox: true }`, `tools/sandboxing.rs` turns that into `SandboxOverride::BypassSandboxFirstAttempt`, and the orchestrator resolves `initial_sandbox = SandboxType::None`. On Linux the sandbox *is* an argv wrapper (`codex-linux-sandbox … -- <cmd>`), so this is not a weakened sandbox but **no sandbox at all**. Three properties make it worse than it sounds. (1) `approval_policy="never"` does not gate this branch - the pin above is irrelevant to it. (2) `read-only` is exposed exactly as much as `workspace-write`: `unsandboxed_execution_allowed` tests only `has_denied_read_restrictions()`, i.e. deny-*read* entries, which neither level emits. (3) The condition is `all()` over segments, so enforcement tracks **the shape of the command the model happened to type**, not any configuration - which is precisely why this read as flaky, unreproducible behaviour. A bare `brokkr check` ran unsandboxed; `sed -n '…' file; brokkr test …` ran sandboxed, because `sed` matched no rule. An agent that hit the sandbox for the first time this way read it as a broken build setup, relocated `CARGO_TARGET_DIR` to `/tmp` - which guaranteed no rule would ever match again, pinning itself in the sandboxed regime - and filled 12G of tmpfs. Verified on 0.151.0 against an operator rules file carrying `["ln","-s"]` and `["brokkr","status"]`: under `--sandbox read-only`, `ln -s /etc/hostname x` created the link inside the workspace and `brokkr status` wrote a row into `~/.local/share/brokkr/history.db`; with `--ignore-rules` both were refused *"Read-only file system"*. The behaviour is documented upstream ("control which commands Codex can run outside the sandbox"), so it is codex working as intended - it is `review`'s advertised guarantee that it breaks. `--ignore-rules` drops the user and project rule layers for this invocation only, leaving interactive codex untouched; it does not touch `CODEX_HOME`, so auth, sessions and rollout discovery are unaffected (redirecting `CODEX_HOME` also kills the bypass, and was rejected for exactly that reason). Residue: the root-controlled `System` layer (`/etc/codex/rules/`) is still loaded, which is correct - it is not the operator's to smuggle. An older codex lacking the flag fails loudly on an unknown argument rather than silently running unsandboxed.
- **Codex is always passed `--ignore-user-config`, so a run is a function of `.review.toml` plus argv and nothing else.** This is the general form of the lesson the two decisions above teach individually: twice the guarantee a profile advertised was silently voided by ambient global codex config the `review` command line gave no hint of - once by `approvals_reviewer = "auto_review"` rewriting the approval policy, once by `$CODEX_HOME/rules/*.rules` disabling the sandbox. Pinning each hole as it is discovered leaves the next one live, so `$CODEX_HOME/config.toml` is dropped wholesale rather than audited key by key. Auth is unaffected - it resolves from `CODEX_HOME` independently of the flag (verified: a run carrying it authenticates and completes normally). **It does not close the rules hole** - rules live outside `config.toml`, so `--ignore-rules` is separately necessary; the measured matrix is `--ignore-user-config` alone = still unsandboxed, `--ignore-rules` alone = sandboxed, both = sandboxed. Two deliberate consequences: a run whose profile sets no `model` takes codex's built-in default instead of the operator's configured one (identical on this host today, and no longer a silent coupling either way), and a profile whose `config` overrides name a custom `model_provider` from the operator's `config.toml` must now define it in the profile.
- **A `workspace-write` codex run derives its extra writable roots from the host (`src/writable_roots.rs`), because closing the sandbox hole broke every build.** Once `--ignore-rules` made build commands genuinely sandboxed, `workspace-write` granted only cwd and `/tmp` - and that is not enough to build anywhere. A real `brokkr check` died at `[error] lock: failed to open lock file: Read-only file system` **before reaching the compiler**, identically whether `CARGO_TARGET_DIR` was inherited, unset, or redirected inside the workspace: the lock lives under `$XDG_RUNTIME_DIR`. So the obstacle order is lock (fatal) → cargo target (fatal) → history db (warning only), and where `./target` points is the *second* problem, not the first. Both fatal paths are properties of the **machine**, not the project - five hosts, two exporting a global `CARGO_TARGET_DIR` onto a separate drive, several repos carrying a `target` symlink at the same shared cache - so restating them per project would put a host fact in fifteen files and get it wrong on every host that was not in front of whoever edited them. `review` derives instead: `$XDG_RUNTIME_DIR`, `$CARGO_TARGET_DIR`, and the resolved `./target` symlink, keeping only those that are absolute and already **outside** cwd, deduplicated (a symlink target carries a trailing slash where the env var does not; `/` is refused outright). This is the one place ambient environment is allowed to influence a run, which is uncomfortable so soon after `--ignore-user-config` removed exactly that coupling - so it is fenced: **`workspace-write` only** (a `read-only` profile derives nothing, since nothing being writable is the whole point of it), only paths a build provably needs, every grant printed at launch with its reason so effective permissions are visible rather than inferred, and passed *before* profile `config` so a profile can restate `sandbox_workspace_write.writable_roots` and win. A profile can name **additional** roots (`writable_roots = [...]`) for what one project needs beyond what any build needs - a data directory, a sibling checkout - and they are added to the derived set rather than replacing it, because the derived set is what makes a build run at all and a profile that replaced it would break the build it was widening. Profile entries pass the same filters, so a `.review.toml` cannot grant `/`, a path containing `..` (which defeats every lexical check - `/..` is absolute, is not a prefix of cwd and is not empty, and codex resolves it to `/`), an **ancestor** of the workspace (`~`, or a `$HOME` that lost its subdirectory, resolves to the home directory and would hand over every repo, `~/.ssh` and review's own logs), a path carrying a control character (unrepresentable in a TOML basic string, so it would render a `-c` codex refuses to parse), or a relative path - all of which hold after expansion. A sibling of the workspace *is* granted: the ancestor check is component-wise, not a string prefix. Every filter runs against the **resolved** path as well as the spelled one, because a lexical check answers "what does this say" while the sandbox binds "what does this reach" - `/srv/cache` may be a symlink to `/`, which passes every string test. The resolved form is what gets granted and recorded, so the log names the directory that actually becomes writable rather than the alias someone typed; a path that does not exist yet cannot be resolved and is taken at its word, since refusing it would break granting a cache directory the build itself creates. Roots are derived against **`project_root`**, not the process cwd: the runners spawn the provider with `.current_dir(project_root)` and `.review.toml` discovery allows launching from a descendant, so deriving from cwd inspected `<subdir>/target` and silently withheld the root a build needed. They support `~`, `$VAR` and `${VAR}`, which is what lets one file serve hosts with different layouts - the deliberate, written-down kind of environment use, unlike the derivation. An entry naming an **unset** variable is dropped with a warning rather than expanded to nothing: `$UNSET/data` would otherwise collapse to `/data`, granting a path nobody named, and a bare `$UNSET` to `/`. A profile that sets `writable_roots` under a `read-only` (or non-codex) profile has them ignored **with a warning**, because silence there is indistinguishable from having granted them. The announcement is printed **once per distinct root set**, not per invocation: a fan-out runs the same profile in the same directory against several archetypes, so per-invocation printing would stack identical blocks above the results instead of saying anything new. Keyed on the set rather than a bare "announced?" flag, so that if roots ever *can* differ between invocations (per-archetype profiles being the obvious next config change) the wider run is not left silently unannounced behind the narrower one's block. Verified: a full `brokkr check` passes inside the sandbox while an ungranted path is still refused, and a profile-granted directory is writable while its own sibling on the same drive is not. The history-db write is deliberately **not** granted - it is a warning, not an error, and agent runs staying out of the operator's build history is a feature.
  - **The derived set is not as tool-agnostic as the paragraph above implies, and the boundary is where the coupling stops being public.** `$CARGO_TARGET_DIR` and the `./target` symlink are genuine cargo/workspace facts that any Rust build has. `$XDG_RUNTIME_DIR` is not - nothing about a Rust build needs it, and it is derived *specifically* because brokkr takes its lock there, which the reason string on the grant says outright. What makes that defensible is that it is a **public environmental contract**: the variable is a standardised XDG interface, the host sets it, and `review` grants the location the host declared. It never predicts anything. When the variable is **unset** brokkr falls back to `$HOME/.cache/brokkr/brokkr.lock`, and granting *that* is a different act entirely - it is brokkr's private implementation detail, discoverable only from brokkr's source, and it would put `review` in the business of predicting the internals of an optional tool it neither selects nor invokes. Every brokkr release could then silently invalidate the sandbox calculation with nothing in `review`'s types, config or dependencies expressing the relationship - reintroducing, as the fix, the exact failure it was fixing. So the unset case is **declared, not derived**: a profile that runs brokkr says `writable_roots = ["~/.cache/brokkr"]`. That belongs in config because whether the agent will run brokkr at all is a property of the profile's workflow, which the profile author knows and `review` cannot. The generic rule: derive from a public contract the host has declared, declare anything that requires knowing a particular tool's internals.
  - This matters because a stripped `XDG_RUNTIME_DIR` is the **common** case, not an edge one: an agent harness's shell does not export it, so `review` launched from one derives nothing, and the codex child - inheriting the same stripped environment - has brokkr fall back into `$HOME`, outside every granted root. Both halves of the failure come from the one missing variable, which is why granting `/run/user/<uid>` by synthesising it is wrong: brokkr would not look there. Measured before the fix: 40 consecutive `workspace-write` runs recorded `writable_roots: null` and every build inside them died at `lock: failed to open lock file: Read-only file system` before compiling. The lock is a **CPU-contention gate** (`check`, `test`, `clippy`, `bench` take it; `fmt` does not), so a partitioned lock costs contention and contaminated benchmark timings - both recoverable - and never build-state integrity, which is cargo's own target-directory locking and is unaffected. That is why the declared-fallback interim is acceptable rather than fail-closed, and why `review` must **not** hold the lock parent-side around a codex run: a run is dominated by model latency, so holding a CPU gate across it would block humans while the CPU sits idle, inverting the gate's purpose.
- **A `workspace-write` codex run is passed `-c sandbox_workspace_write.network_access=true`, because without it codex cannot use unix domain sockets.** This has nothing to do with the network. The seccomp filter codex installs when network access is off (`linux-sandbox/src/landlock.rs`) unconditionally denies `bind`, `connect`, `listen` and `accept`, returning `EPERM`; it carves out AF_UNIX for `socket()` and `socketpair()` only. So an AF_UNIX socket can be created and then used for nothing that needs a pathname. A daemon/worker test suite fails 80 tests at `bind control socket: Os { code: 1, kind: PermissionDenied, message: "Operation not permitted" }` on a path under its own `target/` that cargo had just written test binaries into. **No `writable_roots` entry can fix this** - verified by binding in the *cwd*, which codex grants unconditionally, and getting the identical errno, so there is no path for which it works. That is what distinguishes this from every other sandbox problem in this file, all of which were grants. The `UnixStream::pair` sites in the same suite pass, because `socketpair` has the AF_UNIX carve-out - which is also how the failure disguises itself as flaky, since socket-free crates and socketpair-only tests come back green. Enabling network access is blunt: the filter is all-or-nothing, so this restores AF_INET egress too and codex offers no AF_UNIX-only knob. It is nevertheless **not a widening of what these runs have actually had** - until `--ignore-rules` landed, an operator execpolicy allowlist made build commands bypass the sandbox wrapper entirely, so no seccomp filter was installed and every `workspace-write` run in this tool's history ran with full network access. This makes that explicit and, unlike the bypass, applies to every command rather than the ones whose argv happened to match a rule. Passed before profile `config`, so a profile can restate the key and win. The upstream asymmetry looks like an oversight rather than policy - they carved out AF_UNIX where they noticed it mattered (there is a comment keeping `recvfrom` allowed so `cargo clippy`'s socketpair machinery works) and missed the four pathname syscalls.
- **A `read-only` codex run gets the same network grant, and to do it `review` stops passing `--sandbox` on that path.** The seccomp filter above is not scoped to a sandbox level - it is installed whenever the network policy is `Restricted`, which `read-only` always was - so a read-only run was equally unable to `connect` to a running daemon, use socket options, or open an AF_INET socket at all. The initial scoping of the fix to `workspace-write` ("the reviewer profile has no build to run and so no socket to bind") was simply wrong about what the filter denies: the four pathname syscalls are only half of it. **There is no `sandbox_read_only.network_access`.** `SandboxPolicy::ReadOnly` does carry a `network_access` field, but nothing in the legacy `sandbox_mode` pipeline sets it - `derive_permission_profile` maps `SandboxMode::ReadOnly` to `PermissionProfile::read_only()` with the network policy hardcoded `Restricted`, and only the workspace-write arm consults config. The one surface that can express "read-only filesystem, network enabled" is codex's named-permissions pipeline: a `[permissions.<id>]` profile extending the built-in `:read-only` with `network.enabled = true`, selected by `default_permissions`. The catch, and the reason this is a decision rather than another `-c`, is that `resolve_permission_config_syntax` returns `Legacy` the instant a `sandbox_mode` override is present, and `Legacy` renders `[permissions]` profiles **inert** - so the profile and `--sandbox` cannot be combined, and `review` passes the profile instead of the flag for `read-only` only. Giving up `--sandbox` on the default path for every review run deserved evidence, so `scripts/readonly_network_check.py` measures three configurations against one witness program (`scripts/sandbox_probe.py`). Verified on codex-cli 0.151.0: `write_cwd` is `EROFS` and `read_etc_hostname` is `ok` in **all three**, and the middle configuration - the same profile with network left `Restricted` - reproduces `--sandbox read-only` witness-for-witness, which is what establishes that dropping the flag does not widen the filesystem independently of the network change. Only the socket lines move (`unix_connect`, `unix_sockopt`, `inet_socket_create`, `inet_bind_listen`, `tcp_connect`: `EPERM` → `ok`). Confirmed end-to-end through `review` itself, not just the argv builder. Two details worth keeping: the witnesses are `connect()` and socket options rather than `bind()` on a unix path, because under `read-only` nothing is writable and binding an AF_UNIX socket cannot succeed on filesystem grounds however the filter is set - what a read-only run gains is the ability to *reach* something already listening, plus AF_INET egress; and no proxy is configured, deliberately, because a proxy would put the run in `NetworkSeccompMode::ProxyRouted`, which denies AF_UNIX `socket()` outright and would be worse than the status quo. The Linux path also has no finer knob - `NetworkToml` carries `unix_sockets` and `allow_local_binding`, but only `seatbelt.rs` (macOS) reads them. An older codex without the permissions pipeline fails soft rather than silently wide: it ignores `default_permissions` and falls through to `SandboxMode::default()`, which is `ReadOnly`.
- **The permissions a run launched with are persisted, not just printed.** The fences around the derivation above included "every grant is printed at launch", which turned out to mean *visible in the terminal that launched it and nowhere else*: the sidecar recorded model, env var names and the digest, but neither the sandbox level nor the derived roots, so nothing could answer "which runs could write?" after the fact. The profile name is not an answer - it is a claim about what was requested, and the whole lesson of the two holes above is that what a run requested and what it received are different things. So `ProviderResult` carries `sandbox` (the provider's own vocabulary, `None` for claude) and `writable_roots`, both persisted into the sidecar row, making `jq 'select(.sandbox=="workspace-write")'` and `jq 'select(.writable_roots)'` the queries they should always have been. Derivation moved from `run_codex` up to `invoke` so the values that widen the run are literally the ones recorded - a grant applied from one computation and logged from another is exactly the invisible permission this is meant to prevent. Empty roots are omitted rather than written as `[]`, so a row carrying the field is a row that widened something. A failed launch still records what it asked for; a panicked task records nothing, because it never reached a provider. A profile `config` entry restating `sandbox_workspace_write.writable_roots` wins over the derivation (codex takes the last `-c`), so the recorded roots follow the *run* rather than the derivation - `config_writable_roots_override` parses the override back out, and an explicit `[]` records as empty rather than as "no override". Without that, a profile overriding to `["/secret"]` would be logged with the derived roots and one overriding to `[]` logged as widened when it was not. The level recorded is the **effective** one (`provider::effective_sandbox`), not the caller's `Option`: a `--session` resume carries no profile, so the runner falls back to `read-only` rather than inheriting the resumed session's level, and recording `None` there left every resume row invisible to the very query these fields exist for.
- **Codex is passed `-c model_reasoning_summary="detailed"` so a rollout records why, not just what.** Reasoning items carry `encrypted_content`, sealed server-side and undecryptable locally, and on the default `auto` setting their `summary` arrays come back empty - so a rollout is a command log with no prose anywhere in it. Reconstructing an agent's intent then means inferring it from the command sequence, which is exactly what made the sandbox investigation above expensive. `detailed` populates the summaries for `src/transcript.rs` and `review sessions <id>` to surface. Passed before profile `config` overrides, so a profile can set `none` where the summaries are not worth their tokens.
- Providers get prompts via **stdin pipe**, not CLI args, to avoid shell argument length limits.
- Claude runs with `--permission-mode dontAsk` (uses pre-approved permissions, rejects interactive prompts). Codex runs with `--sandbox read-only`.
- No global config - `.review.toml` lives in the project root.
- claude, codex and grok. kilo/opencode were removed.
- **Grok needs none of the codex failure machinery, because it classifies its own turns.** Its `--output-format json` prints one result object per run carrying `stopReason`, and only `end_turn` means `text` is an answer; a turn cut off mid-flight comes back `cancelled` with `text` holding interim commentary. That is precisely the distinction codex forces `review` to reconstruct from rollout byte offsets and `final_answer` scanning, handed over as a field. So `run_grok` is a plain spawn-and-parse with no watchdog, no transcript forensics, no incident bundle and no auto-resume (which is codex-gated anyway). `interpret_grok_output` sorts a finished run into three outcomes, and the split between the last two is the load-bearing part: **an `Err` means the run never reached a turn** (spawn failure, unknown model, unknown session, a typed `{"type":"error"}` line - checked *first*, since every result field is optional and such a line otherwise parses as a valid empty result and loses its message); **`GrokOutcome::NoAnswer` means a turn ran and grok said why it produced nothing**, and returns `Ok` carrying the session id plus a `grok_no_answer_digest` whose `turn_error` holds the reason. "A turn ran" is established by `GrokResult::ran_a_turn` (a `stopReason`, `sessionId` or `num_turns` is present), not by the JSON merely parsing: every field is optional, so *any* object deserializes into an all-default result, and since `NoAnswer` returns `Ok` it tells `--session` the prompt cache was warmed - an unrecognised pre-turn failure would otherwise mark a cold session warm and get the *next* resume refused as stale. The digest records the **observed** exit code and signal rather than an assumed `1`; a real answer from a process that nonetheless exited non-zero also gets a digest (with `captured: true`, so it does not count as a death) because that status is the only sign something went wrong after the turn finished. Collapsing the second into `Err` - which the first version did - silently costs two things: `invoke` forces `session_id: None` on every error path, so the id grok already minted is dropped and the cut-off turn (the one most worth resuming) cannot be resumed; and `--session` refreshes its cold-cache clock on `output.is_ok()`, so a resume that ran and warmed the cache would leave the clock stale and get the *next* resume wrongly refused. This is the same reason codex returns `Ok`-with-a-death-digest rather than `Err`. The failure still surfaces as one: `exit_code: Some(1)` and `captured: false` make `died_without_answer` true so the process exits 1, and the flat `turn_error` keeps it greppable. Grok also has no verified on-disk rollout, which is the other reason recovery does not apply: there is nowhere to recover from.
- Grok takes no prompt on stdin - `-p` requires a value and `-p -` is read literally as a one-character prompt (it was tested; grok inspected the repo and asked what was wanted). `--prompt-file <path>` is the escape from argument length limits instead, written via `new_temp_file` and removed by `RemoveOnDrop`. `sandbox` maps honestly to grok's `--sandbox`, so unlike claude it is not ignored.
- Subsuming the pbfhogg spec-loop python scripts (codex review/implement roles). Landed: sandbox as a profile field (codex-only), the rich codex digest + `-o` backstop, transcript forensics, resume-path digest parity, transcript `final_answer` recovery for truncated runs, and digest persistence into the audit + sidecar logs (+ `review sessions <id>` artifact view). `goal` needs no code - it's just an archetype whose prompt is `/goal`.
- Planned: a `review add` command to create an archetype from a priming prompt (currently hand-edited).

## Document folders

The standing layout, across every project. Three live folders plus one retired,
split by durability first, subject second.

| Folder | Contents | Rule |
|---|---|---|
| `reference/` | Durable in-repo reference for anyone working on or with the code - how the thing is built and why: `architecture.md`, `technical-implementation-spec.md`, `performance.md` (the durable record of measured numbers over time), invariants, protocol contracts | Citable from source as a source of truth. What it says must be true. |
| `docs/` | Durable in-repo documentation of how the thing is used - guides, CLI reference, the consumer-facing API surface. Sometimes exposed as a hand-edited VitePress gh-pages site | Same must-be-true rule. |
| `notes/` | Transient - work items (`todo.md`), future plans, hypotheticals, bug reports, research, analysis. Things that will die | No truth guarantee. Nothing durable cites it. |
| `plans/` | Retired | Plan documents are transient: they go in `notes/`. |

`reference/` and `docs/` are both durable and both binding. The difference is
subject, not audience: `reference/` covers how the thing is built and why - what
you need in order to change it safely - while `docs/` covers how it is used. A
developer or library consumer reads both. Where a project publishes a site,
`docs/` is what gets published; the folder means the same thing either way.
`notes/` is neither durable nor binding, which is the whole point of keeping it
separate: a document that may be wrong must not sit where a document that must
be right is expected.

**`scripts/` is a fourth, small exception: maintained diagnostics, not
transient investigation.** Each one exists because a claim in `reference`-grade
prose above needs to stay re-testable against a provider that upgrades
underneath us. `ignore_rules_check.py` is the regression check for the sandbox
guarantee (`--ignore-rules`); `flag_matrix.py` measures which isolation flags
actually close the hole; `rules_survey.py` reports which command prefixes an
operator's `~/.codex/rules` exempts from the sandbox; `rollout_commands.py`
dumps a codex rollout's commands and outputs, which is the only readable record
of a run when reasoning summaries are off; `readonly_network_check.py` measures
what a `read-only` run can do with sockets across the three ways of selecting
that level, and is the evidence behind passing a permissions profile instead of
`--sandbox` there - it drives `sandbox_probe.py`, the witness program that runs
*inside* the sandbox and is the one file here not meant to be run directly.
They shell out to `codex` and cost
real turns, so they are run deliberately after a provider upgrade, never from
`brokkr check`. A probe that answers one question and will not be asked again
belongs in `notes/`, not here.

**`research/codex` is a checkout of the codex source, and it is gitignored.**
Not ours, not committed, not guaranteed to be present - but when it is, it is
the authority on every codex behaviour this file asserts, and reading it beats
guessing from a binary or from release notes. Nearly all of the sandbox
archaeology above came out of it: `protocol/src/protocol.rs` for `SandboxPolicy`,
`config/src/config_toml.rs` and `core/src/config/` for how a `sandbox_mode` or
`default_permissions` selection compiles into one, `linux-sandbox/src/landlock.rs`
for what the seccomp filter actually denies. Check `git log -1` and the newest
tag in that checkout against `codex --version` before trusting it - the two
drift, and a config key that exists in the checkout may not exist in the
installed binary. Reading it is not a substitute for `scripts/`: the source says
what should happen, the scripts measure what does.

The dependency direction is therefore one-way. `notes/` may cite `docs/` and
`reference/`; nothing durable may cite `notes/` - not a code comment, not
`docs/`, not `reference/`. A code comment must carry its full context, because
it outlives the note.

**Root-level convention files are exempt.** `AGENTS.md`, `CLAUDE.md`,
`README.md`, `LICENSE`, `CHANGELOG.md` and their kin are found by tooling and by
convention at the repository root, and stay there. These folders govern
documents we chose where to put, not files whose location is dictated.

In `notes/`, `docs/` and `reference/` alike, avoid citing source line numbers -
they drift fast.
