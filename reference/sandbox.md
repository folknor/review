# Sandbox and permissions

The permission machinery shared across providers: `review`'s sandbox
vocabulary, the writable roots a build needs, how the permissions a run
launched with are recorded, and what a `review resume` inherits. The
provider-specific halves are in [codex.md](codex.md), [grok.md](grok.md) and
[claude.md](claude.md) (claude has no filesystem sandbox, so little of this
applies to it).

## The vocabulary

**`sandbox` is `review`'s own vocabulary, translated per provider by `config::sandbox_for`.** The levels (`read-only`, `workspace-write`, `danger-full-access`) are codex's names, kept because they were the documented config surface before translation existed - a fresh set would have silently changed the meaning of every profile already written. Codex takes them verbatim; grok's built-ins are `read-only`/`workspace`/`none`, so the upper two are rewritten. This is not cosmetic: grok cannot resolve an unknown profile name and **refuses to start**, so before the mapping a profile written for codex broke the moment it was pointed at grok, at launch, with an error that reads as a missing config file. `read-only` happens to be spelled identically everywhere, which is why the *default* path was portable by luck rather than design - only an explicit write opt-up ever hit the mismatch. An unrecognised value is passed through verbatim rather than rejected, because grok resolves names against user-defined profiles in `~/.grok/sandbox.toml`: rejecting it would make `review` the reason a valid provider config could not be used, and the provider validates its own vocabulary with a better error than we could write (and fails before running a turn, so a typo is cheap). The three level names are therefore **reserved** - a custom grok profile named `workspace-write` or `danger-full-access` cannot be selected from a `.review.toml` profile. That is the deliberate trade: the point of the levels is that they mean the same thing whichever provider a profile is pointed at, which fails the moment one provider can reinterpret them. Custom profiles have the rest of the namespace.

`sandbox` defaults to `read-only`, so a run with no profile can never modify files; a profile opts up to `workspace-write`. Claude ignores it (see [claude.md](claude.md#sandbox-is-ignored)).

## Writable roots

### `src/writable_roots.rs`

Derives the writable roots a build needs that live outside the workspace: the build lock (`$HOME/.brokkr` - see below), the cargo home (`$CARGO_HOME`, else `$HOME/.cargo`), `$CARGO_TARGET_DIR`, and the resolved `./target` symlink. Keeps only absolute paths already outside cwd (one inside is writable anyway, and granting it would imply a widening that did not happen), normalises trailing slashes so a symlink target and the env var naming the same directory are one grant, and refuses `/`. Profile-supplied roots go through `derive_with`, which expands `~`/`$VAR`/`${VAR}` and refuses an entry whose variable is unset (collapsing it would silently grant `/data` or `/`). `Host` is a trait so the derivation and the expansion are pure functions under test - the developer's own `CARGO_TARGET_DIR` and `HOME` must not decide whether the suite passes. `config_override` renders the codex `-c sandbox_workspace_write.writable_roots=[...]`, TOML-escaping each path; the escaping is tested by *parsing* the result, because a substring assertion cannot distinguish an injected key from the same text safely quarantined inside a string. Applies to `workspace-write` only. Grok gets the same set through a sandbox profile instead (see [grok.md](grok.md#writable-roots)).

### Why roots are derived

**A `workspace-write` codex run derives its extra writable roots from the host (`src/writable_roots.rs`), because closing the sandbox hole broke every build.** Once `--ignore-rules` made build commands genuinely sandboxed (see [codex.md](codex.md#--ignore-rules)), `workspace-write` granted only cwd and `/tmp` - and that is not enough to build anywhere. A real `brokkr check` died at `[error] lock: failed to open lock file: Read-only file system` **before reaching the compiler**, identically whether `CARGO_TARGET_DIR` was inherited, unset, or redirected inside the workspace: the lock lived under `$XDG_RUNTIME_DIR` at the time (it has since moved to `$HOME/.brokkr` - see below). So the obstacle order is lock (fatal) → cargo target (fatal) → cargo home (fatal, but only on a fetch) → history db (warning only), and where `./target` points is the *second* problem, not the first. **The cargo home outlived the other two because it fails conditionally.** `$CARGO_HOME` (`$HOME/.cargo` by default) holds the registry index, the downloaded `.crate` archives, the git checkouts and the package-cache lock, and a workspace whose dependencies are already unpacked needs none of it writable: cargo's `.package-cache` flock degrades silently on a read-only filesystem rather than erroring. So sandboxed agents compiled, linted and ran whole test suites with no grant there at all, which read as the path not being needed. The first build that has to *fetch* a crate - a new dependency, a bump, a lockfile the shared target has not populated - dies before compilation with `failed to open ... registry/cache/...: Read-only file system (os error 30)`, an error naming the cache rather than the sandbox. Observed as exactly that split across two concurrent agents on the same tree: one passed `brokkr check` twice on a warm crate set, the other failed on a single missing `crc32fast`. It meets the determinism test the same way the lock does - `$CARGO_HOME` else `$HOME/.cargo` is cargo's own documented default, not a prediction about a login path. Both fatal paths are properties of the **machine**, not the project - five hosts, two exporting a global `CARGO_TARGET_DIR` onto a separate drive, several repos carrying a `target` symlink at the same shared cache - so restating them per project would put a host fact in fifteen files and get it wrong on every host that was not in front of whoever edited them. `review` derives instead: the build lock, the cargo home, `$CARGO_TARGET_DIR`, and the resolved `./target` symlink, keeping only those that are absolute and already **outside** cwd, deduplicated (a symlink target carries a trailing slash where the env var does not; `/` is refused outright). This is the one place ambient environment is allowed to influence a run, which is uncomfortable so soon after `--ignore-user-config` removed exactly that coupling - so it is fenced: **`workspace-write` only** (a `read-only` profile derives nothing, since nothing being writable is the whole point of it), only paths a build provably needs, every grant printed at launch with its reason so effective permissions are visible rather than inferred, and passed *before* profile `config` so a profile can restate `sandbox_workspace_write.writable_roots` and win. A profile can name **additional** roots (`writable_roots = [...]`) for what one project needs beyond what any build needs - a data directory, a sibling checkout - and they are added to the derived set rather than replacing it, because the derived set is what makes a build run at all and a profile that replaced it would break the build it was widening. Profile entries pass the same filters, so a `.review.toml` cannot grant `/`, a path containing `..` (which defeats every lexical check - `/..` is absolute, is not a prefix of cwd and is not empty, and codex resolves it to `/`), an **ancestor** of the workspace (`~`, or a `$HOME` that lost its subdirectory, resolves to the home directory and would hand over every repo, `~/.ssh` and review's own logs), a path carrying a control character (unrepresentable in a TOML basic string, so it would render a `-c` codex refuses to parse), or a relative path - all of which hold after expansion. A sibling of the workspace *is* granted: the ancestor check is component-wise, not a string prefix. Every filter runs against the **resolved** path as well as the spelled one, because a lexical check answers "what does this say" while the sandbox binds "what does this reach" - `/srv/cache` may be a symlink to `/`, which passes every string test. The resolved form is what gets granted and recorded, so the log names the directory that actually becomes writable rather than the alias someone typed; a path that does not exist yet cannot be resolved and is taken at its word, since refusing it would break granting a cache directory the build itself creates. Roots are derived against **`project_root`**, not the process cwd: the runners spawn the provider with `.current_dir(project_root)` and `.review.toml` discovery allows launching from a descendant, so deriving from cwd inspected `<subdir>/target` and silently withheld the root a build needed. They support `~`, `$VAR` and `${VAR}`, which is what lets one file serve hosts with different layouts - the deliberate, written-down kind of environment use, unlike the derivation. An entry naming an **unset** variable is dropped with a warning rather than expanded to nothing: `$UNSET/data` would otherwise collapse to `/data`, granting a path nobody named, and a bare `$UNSET` to `/`. A profile that sets `writable_roots` under a `read-only` (or non-codex) profile has them ignored **with a warning**, because silence there is indistinguishable from having granted them. The announcement is printed **once per distinct root set**, not per invocation: a fan-out runs the same profile in the same directory against several archetypes, so per-invocation printing would stack identical blocks above the results instead of saying anything new. Keyed on the set rather than a bare "announced?" flag, so that if roots ever *can* differ between invocations (per-archetype profiles being the obvious next config change) the wider run is not left silently unannounced behind the narrower one's block. Verified: a full `brokkr check` passes inside the sandbox while an ungranted path is still refused, and a profile-granted directory is writable while its own sibling on the same drive is not. The history-db write is deliberately **not** granted - it is a warning, not an error, and agent runs staying out of the operator's build history is a feature.

- **The build-lock root is `$HOME/.brokkr`, and the reason it is not `$XDG_RUNTIME_DIR` is the whole lesson.** `$CARGO_TARGET_DIR` and the `./target` symlink are genuine cargo/workspace facts. The build lock never was one - nothing about a Rust build needs it, and it is derived *specifically* because brokkr locks there, which the reason string says outright. `$XDG_RUNTIME_DIR` looked like the safely generic way to spell that, being a standardised XDG variable the host sets, and it was in fact the fragile one: **it is absent from any login that does not go through `pam_systemd`.** Tailscale SSH constructs the child environment itself, so on a host reached that way every shell had it unset while `systemctl --user show-environment` still reported `/run/user/1000` - those two read *different* environments, and the manager's copy is set by systemd for itself and is never evidence about a login shell. Worse, the failure was silent from both ends: `review` derived no root, and brokkr - inheriting the same environment - fell back under `$HOME`, outside every granted root, so the derivation went quiet in exactly the case the build needed it. Measured: 41 consecutive `workspace-write` runs recorded `writable_roots: null` and every build inside them died at `lock: failed to open lock file: Read-only file system` before compiling. All 41 were on the one affected host, which is why this looked like a tool bug and was a host-reachability fact. Granting `/run/user/<uid>` was also far wider than the lock warranted - it holds D-Bus, Wayland, keyring and agent sockets.
- So the fix was to make the location **deterministic** rather than to teach `review` to guess: brokkr now locks unconditionally in `$HOME/.brokkr`. `$HOME` is set by every login path including the ones that drop `XDG_RUNTIME_DIR`, so the root resolves identically from a terminal, an ssh session, an agent harness and inside the sandbox - which is what makes it derivable at all. The test for whether a path may be derived is therefore **determinism, not whether the variable looks standard**. A directory, never a bare lock file at the home root: creating or replacing `$HOME/.brokkr.lock` would require `$HOME` itself writable, handing over every repo, `~/.ssh` and review's own logs. Because it is derived, **no project declares it** - the alternative was one `writable_roots` line in every repo that uses `review`, which is the fifteen-project restatement this module exists to prevent.
- The lock is a **CPU-contention gate** (`check`, `test`, `clippy`, `bench` take it; `fmt` does not - which is why `fmt` kept working while the gate died, and why an agent's one surviving check was `rust-analyzer`, whose false green hid a broken tree). It never protected build-state integrity; that is cargo's own target-directory locking and is unaffected by any of this. Two consequences: a partitioned lock costs contention and contaminated benchmark timings, both recoverable, so failing closed on it would trade a certain total loss for a recoverable partial one; and `review` must **not** hold the lock parent-side around a codex run, because a run is dominated by model latency, so holding a CPU gate across it would block other work while the CPU sits idle, inverting the gate's purpose.

## Recorded permissions

**The permissions a run launched with are persisted, not just printed.** The fences around the derivation above included "every grant is printed at launch", which turned out to mean *visible in the terminal that launched it and nowhere else*: the sidecar recorded model, env var names and the digest, but neither the sandbox level nor the derived roots, so nothing could answer "which runs could write?" after the fact. The profile name is not an answer - it is a claim about what was requested, and the whole lesson of the two codex sandbox holes ([codex.md](codex.md#the-sandbox-guarantee)) is that what a run requested and what it received are different things. So `ProviderResult` carries `sandbox` (the provider's own vocabulary, `None` for claude) and `writable_roots`, both persisted into the sidecar row, making `jq 'select(.sandbox=="workspace-write")'` and `jq 'select(.writable_roots)'` the queries they should always have been. Derivation moved from `run_codex` up to `invoke` so the values that widen the run are literally the ones recorded - a grant applied from one computation and logged from another is exactly the invisible permission this is meant to prevent. Empty roots are omitted rather than written as `[]`, so a row carrying the field is a row that widened something. A failed launch still records what it asked for; a panicked task records nothing, because it never reached a provider. A profile `config` entry restating `sandbox_workspace_write.writable_roots` wins over the derivation (codex takes the last `-c`), so the recorded roots follow the *run* rather than the derivation - `config_writable_roots_override` parses the override back out, and an explicit `[]` records as empty rather than as "no override". Without that, a profile overriding to `["/secret"]` would be logged with the derived roots and one overriding to `[]` logged as widened when it was not. The level recorded is the **effective** one (`provider::effective_sandbox`), not the caller's `Option`: a caller that passes no level still gets `read-only` from the runner, and recording `None` there left such rows invisible to the very query these fields exist for.

## What a resume inherits

**A `review resume` inherits its permissions, model and effort from the session, because they are properties of the session and not of the invocation driving it.** `review resume` bypasses `.review.toml` and so carries no profile, and the runners default to `read-only` - so a resume silently dropped whatever the run that created the session was launched with. The case that makes this concrete is the one auto-resume was built for: a `workspace-write` run dies mid-turn, the operator resumes it, and the session that had been editing files comes back unable to write to them. The failure surfaces as the model reporting a read-only filesystem, which reads as a broken workspace rather than as anything `review` did. `main::inherited_settings` takes the level, roots, model and effort from the session's last sidecar row (`latest_for_session`, already looked up by `resume_record` for the provider and the cold-cache gate) and passes them to `invoke`, so the chain carries forward: each resume records what it launched with, and the next inherits from that row. Three details are load-bearing. The row records the **effective** permissions, not the profile's request, which is exactly what has to be inherited - the recurring lesson of the sandbox work is that those two differ. Roots are passed as *profile* roots rather than as a verbatim list, so they go back through `writable_roots`' filters and are re-derived against **this** host: the build lock is a fact about the machine the resume runs on, not the one that wrote the row. And inheritance is skipped when the row names a different provider, which `resume_record` makes impossible today (the provider is taken from that same row), but the guard stays because a grok level fed to codex is a widening nobody asked for. An old row predating these fields inherits nothing and leaves `read-only` in place; a session with no row at all is not resumed - `resume_record` refuses it, since without a record there is no provider to resume it with. (Grok is the exception on roots: a `review-ws-*` session resumes with its recorded roots verbatim - see [grok.md](grok.md#writable-roots).)

- **Model and effort were originally excluded, and measurement overturned that.** The stated reason was that only `model` was recorded (env values and `config` are not, by design), so a partial restoration would be less predictable than none. What it actually produced: every resume ran on codex's **built-in default model at its default effort**, and since `--ignore-user-config` that default is not even the operator's configured one. Read off the rollouts directly - `turn_context` records the model per turn, and one field session shows `gpt-5.6-sol`/`low` for the fresh turn followed by five resumed turns on a different model entirely, against a profile that named `gpt-5.6-sol` throughout. The sidecar showed the same thing from the other side: every `kind: "session"` row carried `"model": null`. That is not a neutral fallback - it changes the model mid-session, at a different price, with nothing in the output saying so, and on a session whose turns are mostly resumes (5 of 6 above) it decides the majority of the run. So `effort` is now recorded too and both are inherited, rather than neither. The announcement lines (`model: ... (inherited from the session record)`) exist because the failure was *silent*; the same reasoning as printing every writable root. The evidence is codex-specific only because codex is the provider with an on-disk rollout to read `turn_context` out of - the inheritance itself is **provider-agnostic**, so a claude resume now carries `--model`/`--effort` where it previously carried neither, and a grok one carries `-m`/`--reasoning-effort`. That is the same fix, not a widening - but the defect it fixes is **not** universal. Grok stores the model with the session: measured on grok 1.0.40, a session created with `-m grok-4.6` and resumed with no `-m` was still served by `grok-4.6-build`. So for grok the inherited `-m` is redundant rather than corrective, and harmless, since it names the model the session already has. Codex re-resolves the model on every invocation, which is the whole reason this was needed.
- `model` and `effort` are taken from `ProviderResult`, not from the caller's profile, so what is recorded is what the run launched with - the same "record follows the run" rule the writable-roots override obeys, and what makes the chain work: each resume records its inherited values, and the next resume inherits from that row. A profile `config` entry restating `model` or `model_reasoning_effort` is deliberately *not* parsed back out the way `writable_roots` is, because which of `-m` and `-c model=` codex resolves last is not established here and a confident wrong record is worse than an incomplete one.
- Env and profile `config` are still **not** inherited, but for a different reason than the old one: env values are deliberately never recorded and `config` is not recorded at all, so there is nothing to restore from. That is an absence of data, not a judgement about predictability.
- Grok's *served* model is recorded but never inherited - see [grok.md](grok.md#the-served-model).
