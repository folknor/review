# Grok

How `review` drives grok, and why. Everything here is grok-specific; the
cross-provider permission machinery (sandbox vocabulary, derived writable roots,
recorded permissions, what a resume inherits) is in [sandbox.md](sandbox.md).

## Invocation

A fresh run is `grok --session-id <generated UUID>`; `--session` resume is
`grok --resume <id>`. Both carry `--prompt-file <tmp> --output-format json
--permission-mode dontAsk`, then:

- `--sandbox <level>`, translated from `review`'s vocabulary by
  `config::sandbox_for` (`workspace-write` → `workspace`, or the
  content-addressed `review-ws-<hash>` profile of [Writable roots](#writable-roots)).
  A fresh run with no level gets `read-only`; a resume with no recorded level
  gets no `--sandbox` at all, so grok applies the one it saved.
- `--trust`, only for a write run in a project with no trust decision yet - see
  [Folder trust](#folder-trust).
- Profile settings: `model` as `-m`, `effort` as `--reasoning-effort`, `env`.
- `--background-wait-timeout` and the env overrides
  `GROK_FOREGROUND_BLOCK_BUDGET_MS` / `GROK_MAX_FOREGROUND_BLOCK_MS`, all set to
  `GROK_COMMAND_WAIT_SECS` - see [Background commands](#background-commands).

Grok takes no prompt on stdin - `-p` requires a value and `-p -` is read literally as a one-character prompt (it was tested; grok inspected the repo and asked what was wanted). `--prompt-file <path>` is the escape from argument length limits instead, written via `new_temp_file` and removed by `RemoveOnDrop`. `sandbox` maps honestly to grok's `--sandbox`, so unlike claude it is not ignored.

## `src/grok_home.rs`

`review`'s dealings with grok's state dir, through `Grok` - the environment *as the child will see it*: `Grok::resolve` takes `GROK_HOME` and `HOME` from the profile `env` first, then the process (the `CODEX_HOME`/`data_root` trap), and refuses a relative home. Trust is **read, not written** - grok writes it via `--trust`. `check_trust` returns the decision grok would reach and refuses where the grant would be wrong or cannot work: a covering `trusted = false` (grok's grant would overwrite it), a store grok cannot parse (grok would trust nothing), a symlinked store (grok refuses to load it), a grok-managed `-w` worktree (keyed through grok's sqlite registry, which `review` cannot read). `decision` models grok's gate: it queries with the *workspace key* (`folder_trust::decide_inputs`), and `is_trusted` only counts entries that prefix the key and share its workspace id - so the key's own entry is the only one that can decide (a `false` on a subdirectory is never consulted; one reviewer claimed otherwise, and grok's source settled it). `workspace_key` models grok's key: canonical git root, linked worktree collapsed onto its main checkout, the dir itself when the root is the user's home. `profile_name` names a root set by content (`review-ws-` + FNV-1a of the sorted, deduplicated set - FNV because `DefaultHasher` is not stable across Rust releases, pinned by a test); `ensure_profile`/`merge_profile` create that profile in `sandbox.toml` (`extends = "workspace"`, `read_write` = exactly the set, inline layouts accepted) and never modify one - an existing profile whose roots or base (absent reads as `workspace`, as grok does) no longer match its name is refused as edited. `TrustDocument`/`SandboxConfig` mirror grok's serde types field for field, because grok deserializes each file whole and drops all of it on one bad entry. `locked_update`: exclusive `flock` on `<file>.lock` (grok's convention for its trust store; grok never writes `sandbox.toml`, so there it serializes `review` against itself), `toml_edit`, unique 0600 temp renamed into place, and a path through a symlink refused - grok will not load a trust-boundary file through one. `trust_failures` picks grok's `folder trust` failure lines out of stderr. `untrusted_hint` explains a cancelled turn. `cancel_cause` reads a session's `events.jsonl` (`turn_ended.cancellation_category` of the last turn, plus the tool whose `permission_resolved` was not `allow`); `session_events` finds that file by scanning `sessions/*/<id>/` so grok's cwd-encoding scheme is never re-implemented.

The module's tests resolve their scratch directory (`std::fs::canonicalize`) before use. The trust-boundary check refuses a path with *any* symlinked ancestor, and `target/` is itself a symlink on hosts that keep the build cache on another drive, so an unresolved scratch path made every store "reached through a symlink" before a test had planted one of its own.

## Turns classify themselves

**Grok needs none of codex's death-detection machinery, because it classifies its own turns.** Its `--output-format json` prints one result object per run carrying `stopReason`, and only `end_turn` means `text` is an answer; a turn cut off mid-flight comes back `cancelled` with `text` holding interim commentary. That is precisely the distinction codex forces `review` to reconstruct from rollout byte offsets and `final_answer` scanning, handed over as a field. So each grok turn (`run_grok_turn`) is a plain spawn-and-parse with no watchdog, no transcript forensics, no incident bundle, and no codex-style auto-resume (which is codex-gated). The one loop grok *does* get - waking the model for background results it never read - answers a different question (did the model see its own work?) and is described under [Background commands](#background-commands). `interpret_grok_output` sorts a finished run into three outcomes, and the split between the last two is the load-bearing part: **an `Err` means the run never reached a turn** (spawn failure, unknown model, unknown session, a typed `{"type":"error"}` line - checked *first*, since every result field is optional and such a line otherwise parses as a valid empty result and loses its message); **`GrokOutcome::NoAnswer` means a turn ran and grok said why it produced nothing**, and returns `Ok` carrying the session id plus a `grok_no_answer_digest` whose `turn_error` holds the reason. "A turn ran" is established by `GrokResult::ran_a_turn` (a `stopReason`, `sessionId` or `num_turns` is present), not by the JSON merely parsing: every field is optional, so *any* object deserializes into an all-default result, and since `NoAnswer` returns `Ok` it tells `--session` the prompt cache was warmed - an unrecognised pre-turn failure would otherwise mark a cold session warm and get the *next* resume refused as stale. The digest records the **observed** exit code and signal rather than an assumed `1`; a real answer from a process that nonetheless exited non-zero also gets a digest (with `captured: true`, so it does not count as a death) because that status is the only sign something went wrong after the turn finished. Collapsing the second into `Err` - which the first version did - silently costs two things: `invoke` forces `session_id: None` on every error path, so the id grok already minted is dropped and the cut-off turn (the one most worth resuming) cannot be resumed; and `--session` refreshes its cold-cache clock on `output.is_ok()`, so a resume that ran and warmed the cache would leave the clock stale and get the *next* resume wrongly refused. This is the same reason codex returns `Ok`-with-a-death-digest rather than `Err`. The failure still surfaces as one: `exit_code: Some(1)` and `captured: false` make `died_without_answer` true so the process exits 1, and the flat `turn_error` keeps it greppable. Grok also has no verified on-disk rollout, which is the other reason recovery does not apply: there is nowhere to recover from.

## Folder trust

**A grok write run trusts its project first, because grok cancels edits in an untrusted folder.** In a folder with no trust decision in `trusted_folders.toml`, every file edit raises a permission prompt; `--permission-mode dontAsk` resolves it `cancelled`, and grok ends the *whole turn* rather than handing a denial back to the model. The sandbox level is irrelevant - `--sandbox workspace` was passed correctly throughout. Observed on grok 1.0.40: six `workspace-write` fixers in an untrusted checkout each read, diagnosed and announced their fix, then were cancelled at their first `search_replace` after 5-16 minutes. The same edit with the same flags succeeds in a trusted folder (verified A/B). Running `review` in a project with a profile that asks for `workspace-write` *is* the operator's decision that this project may be written - whether that profile lives in the project's `.review.toml` or in the global config, the invocation is the opt-in - so a grok write run launches with grok's own hidden `--trust` flag (`xai-grok-pager/src/app/cli.rs`, honoured in headless mode by `headless.rs` via `folder_trust::grant_folder_trust`) rather than making a human repeat that decision in grok's TUI. An earlier version wrote `trusted_folders.toml` itself; review found its model of grok's key diverged for linked worktrees and a dotfiles repo at `$HOME`, so an entry landed where grok never looks. `--trust` uses grok's own key and lock, so that class of bug cannot exist - verified on 1.0.40 against a scratch `GROK_HOME`: launched from `piners/target/grokperm`, it recorded `/home/folk/Programs/piners`, before the auth check. **What a grant actually is**, which the first version understated as "may edit": grok's folder trust is VS-Code-style workspace trust, and it gates whether the repo's own `.grok` MCP/LSP config may spawn servers - "arbitrary commands from repo-controlled config files" (`trust.rs` module docs). And it is **permanent and host-wide**: the entry stays in `trusted_folders.toml`, so from then on every grok session in that repo, the operator's interactive ones included, runs that config without asking. Accepted because the repos `review` is pointed at are the operator's own and launching a `workspace-write` run there is their explicit opt-in to letting an agent change the repo - but never silently: `--trust` is passed **only when the project has no decision yet** (an already-trusted project gets no flag), the run that grants it prints what it means (`grok: trusting <key> permanently ... grok will also run this repo's .grok MCP/LSP config without asking`), and the key lands in the sidecar as `grok_trust` (`jq 'select(.grok_trust)'` lists every grant `review` ever made) - but only after the store is re-read post-run and shows it: a grant grok fails to save (`KeyMoved`, `Unreadable`, a process-local fallback) is printed only to grok's stderr, so `trust_failures` surfaces it as a warning and nothing is recorded, because "we passed `--trust`" is not "the folder is now trusted". Limits that keep it from being ambient widening: grok's grant covers only grok's key for the project; `review` **never lets it override a `trusted = false`** on that key (grok's grant would; `check_trust` refuses the launch - automating a yes must not overturn a recorded no); a store grok cannot parse is refused (grok would trust nothing); a grok-managed `-w` worktree is refused, because its key comes from grok's sqlite registry and a wrong guess could let the grant land on a declined source repo (grok consults that registry only for paths under `$GROK_HOME/worktrees` - `worktree_record_for_cwd_in` - so that is exactly the set refused). **Residual race, accepted**: the declined-check and grok's grant are separate reads of the store, and grok offers no "grant unless declined" operation, so a `false` written between them would be overwritten. `run_grok` re-checks immediately before spawn, shrinking the window to grok's startup; closing it needs grok. Likewise the symlink refusal is check-then-write; exploiting that needs write access to the grok home, which already means editing the config directly, so it is out of the threat model. A `read-only` run passes no `--trust` and touches no file: reads work untrusted. It also does **not** use `--always-approve`/`bypassPermissions`: those disable approval for everything, where trust is scoped to one folder. For a turn that is cancelled anyway, grok's own `cancellation_category` and the refused tool from `events.jsonl` are appended to `turn_error`, with the trust hint when it applies. Grok's reported `num_turns` and `usage` now populate the digest too (input codex-shaped, i.e. including cache reads), so a cancelled run no longer reads as one that spent nothing.

## Writable roots

**A grok write run gets exactly the same derived writable roots as codex, through a content-addressed sandbox profile `review` creates in `~/.grok/sandbox.toml`.** Grok's built-in `workspace` profile writes only to the workspace, the grok home and the temp dirs, so the second wave of fixers - trusted now - edited fine and then every `brokkr test` died at `lock: failed to open lock file` on `~/.brokkr`, exactly as codex did before `writable_roots.rs`. Two fixers worked around it by moving `HOME` under `target/`, which silently took a private brokkr lock and bypassed the host's build-contention gate. Grok offers no flag or env var for extra writable paths (checked in `research/grok-build`: `config.toml`'s `[sandbox]` and `GROK_SANDBOX` select a profile *by name* only; `GROK_HOME` would move auth, sessions and trust with it, the `CODEX_HOME` problem again). The one surface is a named profile, in the global file or a project `.grok/sandbox.toml`. The project file was rejected because it would put a host-specific generated file into every repo. `review` therefore derives the roots exactly as for codex (same `writable_roots::derive_with`, same filters, same announcement, same sidecar record), names a profile for that exact set (`review-ws-<hash>`), creates it if it is missing, and launches with `--sandbox review-ws-<hash>`. **One profile per distinct set, not one shared profile.** The first version shared a single `review-workspace-write`; sharing forces it to be union-only (a run that rewrote it to its own roots could strip a concurrent run's grants between the write and that run's grok starting), and union-only meant a root one project's `.review.toml` added became writable to every later grok write run on the host - broader than codex, where each run gets exactly its own roots. A codex review flagged it. Content-addressed profiles restore the codex property: a run gets exactly its set; a profile is created once and never modified (so concurrent runs cannot interfere, and there is nothing to prune); two runs with the same set share one entry. The cost is one entry per distinct set in the operator's `sandbox.toml` - in practice one per host, plus one per project whose profile adds extra roots. The recorded `writable_roots` is exactly the profile's set. The whole resulting file is validated against mirrors of grok's serde types before it is written, because grok drops the entire global file on one bad entry - and then a checked-out repo's `.grok/sandbox.toml` could define a `review-ws-*` name itself (project profiles only lose to a *loaded* global of the same name). A symlinked `sandbox.toml` (or grok home) is **refused**, not followed: grok lists `sandbox.toml` among its trust-boundary files and refuses to load one through a symlink (`resolve_trust_boundary_sources`, `ensure_grok_trust_boundary_slots`), so a profile written through a dotfile manager's link could never be used - an earlier version followed the link and wrote a profile grok would not load. The grok home is resolved as the child sees it, profile `env` `GROK_HOME` and `HOME` included - the `CODEX_HOME`/`data_root` trap again. **Resume**: grok fixes a session's sandbox profile for its lifetime and refuses an explicit `--sandbox` that differs from the saved one (`resolve_startup_sandbox` → `Conflict`), so `grok_write_launch` passes the recorded name through unchanged. A session recorded under a `review-ws-*` profile resumes under that exact profile with the roots **recorded with it, verbatim** - not re-derived, because the name pins one set and a resume on another host would derive a different one; the recorded roots are checked to hash back to the name (a mismatch is a launch error), and the profile is recreated from them if someone deleted it, which grants nothing the session did not already have. One recorded as `workspace` (created before these profiles existed) resumes as `workspace` with trust ensured and no extra roots, because it cannot be moved. One with **no** recorded level (an old row, or none) gets no `--sandbox` at all, so grok applies the saved one - forcing `read-only` there made every such write session unresumable - and no trust or root setup, since nothing says it writes. A setup failure (unparseable file, edited profile, declined trust, symlink, grok worktree, roots not matching the recorded profile, relative `GROK_HOME`) is a launch `Err`, because running anyway reproduces the lock and cancellation failures more expensively. The setup runs in `spawn_blocking`: file I/O plus a `flock` another `review` may hold (grok never writes `sandbox.toml`; the lock serializes `review`'s own fan-out, where two runs may create the same profile at once). Grok's `workspace` leaves `restrict_network = false` (confirmed in `profiles.rs`), so the unix-socket grant codex needs has no grok counterpart.

## Background commands

**Grok shell commands stay in the foreground until they finish, so reading a build's result does not depend on the model remembering to wait.** Grok moves any command that blocks longer than 15s to the background (`toolset.bash.auto_background_on_timeout`, on by default). A model that then calls `get_command_or_subagent_output` with a timeout blocks within the same turn and reads the result - session `db7ea2b1` did exactly that for two `brokkr test` runs, guided by grok's bundled `long-running-background-tasks` skill. A model that instead ends its turn loses the result: in `-p` mode `headless.rs` waits only for the task to *finish* and exits once `pending_bg` is empty, and the completion is queued as a wake-up for a model that never gets another turn. Two second-wave fixers ended that way ("I'll read the result when that build finishes"), and a live probe showed `brokkr test` passing 13s after grok had exited. Which of the two happens is model behaviour, and the failure is silent - a run that looks finished with no report - so `review` enforces the outcome instead of hoping for it, in two layers. **(1) Keep commands in the foreground where grok allows it.** The auto-background switch is `config.toml`-only (not on the `GROK_CONFIG` allowlist, `config_override::OVERLAY_ALLOW_PATHS`), and turning it off would not help - a non-backgroundable command is *killed* at `min(timeout, max(5min, configured))` instead - so `run_grok_turn` sets grok's own env overrides, `GROK_FOREGROUND_BLOCK_BUDGET_MS` (the 15s budget) and `GROK_MAX_FOREGROUND_BLOCK_MS` (the 5-minute kill cap for a command that *cannot* be backgrounded - not the normal path), to `GROK_COMMAND_WAIT_SECS` (20 minutes; a profile `env` can restate either). A command then holds the foreground for `min(model's timeout, 20min)` - the model may ask for up to 10h because production grok always sends `max_timeout_secs` = 10h (`PRODUCTION_MAX_TIMEOUT_SECS`; a reviewer's reading of the 5-minute `DEFAULT_MAX_TIMEOUT_MS` as the ceiling missed that). Verified: a 30s command ran in the foreground and its output was reported in the same turn. That cannot be a guarantee: the *model* picks the timeout (120s when it picks none, `DEFAULT_TIMEOUT`, raisable only via `config.toml`), and can background work on purpose. **(2) Wake the model for anything it missed - the actual guarantee.** `--background-wait-timeout` is raised to the same 20 minutes (default 600s, after which grok *kills* the pending work), so a command the model walked away from still finishes and leaves its output in the session. Then `run_grok` reads grok's own update stream (`grok_home::unread_background_results`) for work the model never saw: a `task_completed` or `subagent_finished` after the last *real* turn end; a `task_completed` marked `will_wake` that no *later* turn (one whose prompt arrived after the completion) has ended since; or a `task_backgrounded`/`subagent_spawned` in the latest turn that never finished. The `will_wake` rule came from a live test: a warm `brokkr test` the model had backgrounded finished *before* the model's turn ended, so "completed after the last turn end" called it read - but grok does not hand a background result to the running turn, it queues it as a wake-up, and that message sat unread after the turn. Grok records the difference on every completion: `will_wake: true` / `block_waited: false` when the model was not waiting (both lost sessions), `will_wake: false` / `block_waited: true` when it was blocked on it and got it in-turn (`db7ea2b1`). Subagents carry no such flag, so a background subagent finishing mid-turn is still judged by the turn-end rule alone - the one known gap. If there is any, it resumes the session (same sandbox, model; no `--trust`) with a prompt that **contains the results** (`grok_home::wake_prompt`: each command's exit status and the last 16 KB of its output from grok's own `task_snapshot`, with the full log's path; a plain "did NOT finish" for work grok stopped at exit; a subagent's status), and repeats until a turn ends with nothing unread. Carrying the result rather than pointing at it is the load-bearing part, and a second review forced it: a first version only told the model to go and read the output, and a model that ignored that and ended its turn produced a clean-looking turn boundary with the result still unseen. A prompt that contains the result has delivered it by being sent. Details a first review found: grok starts its *own* wake turns when background work finishes (prompt ids `task-completed-*` etc., `notification_bridge.rs`), and one torn down at exit writes a non-`end_turn` `turn_completed` that must not count as the model reading anything; work that never finished is only counted within the latest turn, because each resume is a new grok process that can never finish an earlier one's task (safe to drop after that turn *because* the wake prompt told the model); and persistent monitors (`task_backgrounded` with `monitor_description`) never complete by design and are not counted. The run **fails closed**: if grok's home or the session's update log cannot be read, or a line of it does not parse (grok flushes the log before a headless process exits, so a bad line means something is wrong), the run fails rather than passing unverified. It also fails at `GROK_MAX_WAKES` (10) - each wake delivers what it names, so only a model that keeps starting new background work reaches it. It does not wake after a stated failure (the codex `stated_failure` lesson; that digest already fails the run), and a wake turn that fails to launch keeps the first turn's output and session id. Each wake is printed, the answer is prefixed with the wake count, and cost, turns and token usage are summed across every turn into the run's digest. There is no overall wall-clock cap: each wake is one model turn plus at most one 20-minute background wait. This is the codex auto-resume idea applied to a different gap: codex's is a one-shot retry for a death; grok's is a loop until a verifiable condition holds. Side finding: grok honours the repo's Claude Code permission file (`.claude/settings.local.json`) - a probe's `sleep` was refused by its deny rules - so an agent's allowlist shapes what a grok run can execute too.

## The served model

**Grok's served model is recorded, never inherited.** Grok reports in its result JSON (`modelUsage` keys) which model actually served the run, and it is a *different name* from the one selected: `-m grok-4.7` is served as `grok-4.7-build`, which `grok models` does not list and `-m grok-4.7-build` refuses as an unknown model id. It is persisted as `served_model` (with `cost_usd` from `total_cost_usd`) because it is the truthful record of what ran, but it is deliberately absent from `SessionRecord`, so no resume can read it back into `-m` and fail the launch. `model` keeps holding the selectable name. Record-only today; nothing consumes either field.

Grok also stores the model with the session, so the `-m` a resume inherits is redundant for grok rather than corrective - see [sandbox.md](sandbox.md#what-a-resume-inherits).

## Source checkout

`research/grok-build` is a gitignored checkout of grok's source. Like
`research/codex` (see [codex.md](codex.md#source-checkout-and-diagnostics)) it
is not ours and not guaranteed to be present, but when it is it is the
authority on grok behaviour asserted here: `xai-grok-pager/src/app/cli.rs` for
the hidden `--trust` and `--background-wait-timeout` flags, `headless.rs` for
what `-p` mode waits for, `trust.rs`/`folder_trust` for the trust key, and
`profiles.rs` for the built-in sandbox profiles.
